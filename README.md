# data-curator

Change management for a corpus of Environmental Product Declarations.
Corrections, supersession and expiry, with a full audit trail, on Google Cloud.

## Stack

| Concern | Technology |
| --- | --- |
| API | FastAPI on Cloud Run, private, IAM-authenticated |
| Webhooks | FastAPI on Cloud Run, public, HMAC-SHA256 verified |
| Queue | Pub/Sub, push subscription, dead-letter topic |
| Processing | FastAPI on Cloud Run, push subscriber |
| Storage | BigQuery, partitioned and clustered |
| Scheduling | Cloud Scheduler with OIDC |
| Secrets | Secret Manager, mounted at container start |
| Build | Cloud Build to Artifact Registry, Dockerfile per service |
| Model | OpenAI `gpt-5-mini` behind a provider protocol |
| Schemas | Pydantic v2, enforced structured output |

Python 3.12 in the containers, 3.14 locally.

## Model

An EPD record changes for three reasons:

1. A reviewer finds an error in a value.
2. The manufacturer publishes a new version, superseding the old one.
3. The declaration reaches its validity date and expires.

All three are one entity, a **change request**. The first two arrive over HTTP,
the third is generated by a scheduled job, and from that point they share one
code path.

## Architecture

```
  reviewer ──────> API ─────┐
  manufacturer ──> webhook ─┼──> Pub/Sub ──> worker ──> BigQuery
  scheduled job ────────────┘    (+ DLQ)       │
                                               │  screen()    deterministic rules
                                               │  triage()    model, conditionally
                                               │  finalise()  deterministic rules
```

Three ingress paths, one queue, one consumer. The API and the webhook receiver
validate shape, publish, and return 202. Neither holds write permission on the
datastore. The scheduled job runs inside the worker and publishes expiry
requests back onto the same topic. The worker is the only component that writes
to BigQuery.

## Decision pipeline

`domain/pipeline.py` composes three stages.

**`screen()`** applies deterministic rules: field path resolution, type
stability, and whether the change would introduce a validation error the record
does not already carry. Most requests terminate here.

**`triage()`** is reached only by requests the rules cannot settle. The model
receives product identity, cross-referencing physical properties, declared
impacts and the proposal, and returns a classification, a confidence score and a
rationale under an enforced schema.

**`finalise()`** converts that into an outcome under rules the model cannot
influence:

- Changes to published figures (`impacts.*`, `date`, `epd_code`,
  `reference_unit`) always route to human review at any confidence. These values
  propagate into third-party calculations and cannot be silently retracted.
- Confidence below 0.85 routes to human review.
- A classification of `implausible` rejects.

Policy lives in `domain/changes.py` as testable code. None of it is expressed in
the prompt.

## Validation

`domain/validation.py` holds deterministic consistency checks:

- GWP components against the declared total
- Density against thickness and the declared conversion ratio
- Material percentages against 100%, asymmetric (over is an error, under is a
  warning, since range midpoints legitimately fall short)
- Packaging excluded from composition
- End-of-life routes summing to 100 per material
- Variant reference integrity, `flag` consistency, C2C and lifespan pairing

Checks return `Issue` objects with a field, a severity and a message. `screen()`
compares the issue set before and after a proposed change, so a change is judged
on whether it makes a record worse.

## Webhooks

`services/webhook` receives republication events from manufacturer systems at
`POST /webhooks/{source}`.

Verification is HMAC-SHA256 over `timestamp + "." + raw body`, compared with
`hmac.compare_digest`. Timestamps outside a five minute window are rejected in
both directions, which bounds replay of a captured request and rejects a forged
future timestamp buying an unlimited window. Nothing is parsed or acted on
before verification, and a failed request receives a bare 401 with no
explanation.

One signing secret per source, held in Secret Manager and mounted as
`WEBHOOK_SECRET_<SOURCE>`. A leaked key compromises one sender, and revoking a
sender is one secret version.

A verified payload becomes a `ChangeRequest` with `kind=record_replacement` and
enters the same queue as everything else, so it is schema-validated and routed
to human review by existing code.

`scripts/simulate_manufacturer.py` sends genuine signed requests, with
`--bad-signature`, `--stale` and `--tamper` for the rejection paths.

The receiver is the only component reachable without a Google identity, and
Google Cloud has no hard spending cap, so it is not left deployed.
`scripts/webhook_demo.sh` deploys it at `--max-instances=1`, runs all four
cases, and deletes it on exit. `--keep` leaves it running.

## Data model

BigQuery dataset `curator`, EU multi-region.

| Object | Type | Contents |
| --- | --- | --- |
| `epd_records` | table | Versioned records, append-only, clustered by `product_id` |
| `epd_current` | view | Highest version per `product_id` |
| `epd_expiry_status` | view | Expiry state derived from `CURRENT_DATE()` |
| `change_requests` | table | Immutable proposals, partitioned by `submitted_at` |
| `change_events` | table | Decisions and reviews, partitioned by `occurred_at` |
| `change_status` | view | Latest event per request |
| `review_queue` | view | Requests awaiting a human, with waiting time |
| `agent_registry` | table | Agents, owners, model, eval scores, review date |
| `agent_registry_attention` | view | Agents unevaluated or overdue review |
| `reconciliation_runs` | table | One row per scheduled run |

Applying a change writes version *n+1* and leaves *n* intact, so historical
state stays queryable. This also avoids BigQuery's lack of primary keys:
enforcing uniqueness at write time would require a `MERGE` per change or a
read-then-write that races under concurrency.

Cost, token counts and latency are recorded per decision in `change_events` and
emitted as structured JSON to Cloud Logging.

## Scheduled reconciliation

`domain/reconcile.py`, invoked nightly against `POST /jobs/reconcile` on the
worker. Two failure classes:

- **Failures**: records past their validity date, requests stuck in review
  beyond an SLA, dead-lettered messages.
- **Drift**: rejection rate above threshold on a sufficient sample, mean model
  confidence below threshold. These raise no errors of their own.

Expired records are not edited in place. The job submits an expiry change
request through the same queue, producing the same audit trail as any other
change.

## Evaluation

`eval/cases.json` holds 54 labelled change requests derived from the corpus,
generated by `eval/generate_cases.py`. Cases may corrupt a record before
proposing a change, which is how genuine corrections are represented alongside
bad proposals.

`eval/run_eval.py` exercises the production `decide()` path and reports two
independent figures: accuracy against the labelled outcome, and unsafe applies,
meaning changes auto-applied that should have been rejected or reviewed. The run
fails on any non-zero unsafe count regardless of accuracy, because the two error
directions have asymmetric cost.

`domain/providers/stub.py` is a deterministic offline triager implementing the
arithmetic relationships the prompt describes. It requires no network and serves
as the baseline a paid model has to beat.

`scripts/register_agent.py` writes the eval summary into `agent_registry`.

## Running

Local, no cloud dependencies:

```bash
python -m pytest tests/ -q
python eval/run_eval.py                      # stub provider, free
python eval/run_eval.py --provider openai    # requires .env
```

Cloud, in order:

```bash
bash scripts/setup_gcp.sh          # topics, dataset, service accounts, IAM, secrets
gcloud secrets versions add openai-api-key --data-file=-
python scripts/seed_bigquery.py    # load the corpus
bash scripts/deploy.sh             # build, deploy, wire the subscription
bash scripts/setup_scheduler.sh    # reconciliation job, created paused
bash scripts/smoke_test.sh         # end-to-end verification
bash scripts/webhook_demo.sh       # deploy the receiver, exercise it, delete it
```

The reconciliation job is created paused and runs on demand with
`gcloud scheduler jobs run curator-reconcile --location=europe-west1`. Unpause
it only where something is watching it.

`bash scripts/teardown.sh` deletes the services, the scheduler job and the push
subscription, keeping data and secrets. `--images` and `--data` extend it.

`. scripts/gcp_env.sh` exports shared configuration and resolves the Cloud SDK's
bundled Python for `bq`, which does not locate an interpreter under Git Bash on
Windows.

`seed_bigquery.py --replace` truncates `epd_records` and reloads at version 1,
discarding version history.

## Design notes

**Queue between ingress and processing.** Decouples availability, decouples
scaling of millisecond validation from multi-second inference, and enables
replay from the dead-letter topic. The API blocks on publish confirmation before
returning 202, so a Pub/Sub outage surfaces as a 503 instead of silent loss.

**Public surface isolated and ephemeral.** Cloud Run authentication applies per
service and not per path, so a webhook endpoint on `curator-api` would expose
`/changes`, `/reviews` and `/epd` to the internet. The receiver is its own
service holding publish rights on one topic and read access to its own signing
secrets, and nothing else. It is deployed for a demonstration and deleted
afterwards, since an endpoint that does not exist cannot be attacked.

**Single writer.** The worker holds `dataEditor` on the dataset, the API holds
`dataViewer`. One place where the append-only invariant can be violated.

**Expiry as an event.** Records load as `active` regardless of date, so every
expiry has an originating request, a decision and a detection timestamp.

**`--ack-deadline=60`.** Measured p95 for a model call plus the BigQuery
writes that follow it exceeds the 10s default, which causes redelivery of
messages still being processed successfully.

**Dockerfile over source deploy.** A source deploy uploads a single directory,
preventing two services from sharing `domain/`. A Dockerfile takes the
repository root as build context.

**Provider protocol over a framework.** Triage is a single call with no loop, and
`responses.parse` provides schema-enforced output natively. `Triager` is a
five-line protocol and an additional backend is one class. The framework's
import cost is also paid on every cold start of a scale-to-zero service. The
tradeoff is the loss of LangSmith tracing, replaced by explicit token, cost and
latency fields on every log line.

## Deployment notes

- Google's front end intercepts `/healthz` on Cloud Run and returns an HTML 404
  before the request reaches the container. The health endpoint is `/health`.
- `bq add-iam-policy-binding` on a dataset returns `This feature requires
  allowlisting` on standard projects. Dataset grants go through the access list;
  see `scripts/grant_dataset_access.py`.
- Cloud Scheduler POSTing an empty body receives 411. `--message-body={}`
  supplies a Content-Length.
- The worker requires `pubsub.publisher` on the changes topic for expiry
  requests.

## Known limitations

The eval under-tests the model. Cases the model handled well were absorbed into
deterministic rules, so headline accuracy largely reflects the rule layer.
